# Chanel Fabric ingestion demonstrations

The [specification](SPECIFICATION.md) defines three isolated comparisons using the same staged CSV bytes: [file-backed materialized lake views](demo-1-materialized-lake-views/), [Eventhouse and OneLake availability](demo-2-eventhouse/), and [OneLake events with Copy](demo-3-onelake-events-copy/). The [shared producer](demo-data-generator/) runs as a bounded Fabric notebook through a wrapper pipeline in its own workspace, not as a local presentation-time process.

The default one-minute source cadence is not a downstream visibility guarantee. Demo 1 uses managed MLV refresh (document the actual supported interval); Demo 2's five-minute OneLake target is not an SLA and its propagation latency is not reported; Demo 3 requires a real event and Copy run. See the specification for acceptance criteria and feature-specific blockers.

## Configuration and prerequisites

Copy `config.example.json` to a private, untracked location and fill in the resolved IDs, names, feature settings and bounded run parameters. The `workspace_name` defaults contain `{prefix}`; each track expands it using the effective `--prefix`. The config is version 1 and consists of shared `environment`, `tenant_id`, `subscription_id`, `capacity`, `authentication`, `execution`, and `data` objects and `demo-1`, `demo-2`, `demo-3`, and `shared` track objects. Each demo's `verification_timeout_seconds` applies per batch and takes precedence over `execution.verification_timeout_seconds`; `execution.poll_interval_seconds` controls validation polling. Null IDs must be resolved and recorded by each track before it reports readiness. Configuration may contain secret **references**, never tokens or secret values. State files and logs must contain only sanitized data.

Use the signed-in MCAP identity where supported. In each PowerShell process set `$env:AZURE_CONFIG_DIR = "$HOME\.azure-mcap"` before invoking Azure CLI-backed operations; verify the active tenant, subscription and capacity. The configured identity alone does not grant cross-workspace permissions. The user has approved access and other changes needed for live testing; determine and record the least-privilege scope before making changes. All feature, permission, API-coverage and charge checks in the specification remain required.

### Current preflight limits

Read-only preflight found `fabricadbmirror` active at F8, and a capacity listing available to an administrator or contributor returned it. Tenant settings show workspace/item creation and service-principal APIs, workspace access and connections enabled, with no included or excluded groups reported. These observations do **not** prove workspace creation, notebook execution, or effective permissions. Workspace creation requires `Workspace.ReadWrite.All` and capacity contributor/admin access; verify the resulting workspace's capacity ID.

A producer workspace identity would require explicit Contributor access on its own workspace before running its notebook. The proposed least-privilege model is folder-scoped Files ReadWrite and Lakehouse item Read for Demo 1/3 destinations, plus KQL table-level ingestor for Demo 2. Table-level ingestor also requires database-level access before assignment; the minimum sufficient database role and ingestion-status tracking permissions are unverified. The user approved changes needed for live testing, but these are proposals, not existing grants. Confirm exact supported identity and access paths before making changes; do not broaden permissions. The producer owner reports a completed no-sales pipeline probe with matching `executionData.parameters`, Lakehouse binding and user identities for storage and Kusto tokens; a Demo 3 preflight sentinel was written, read and deleted outside the incoming folder. Real KQL ingestion, incoming-file delivery and event behavior remain unverified, and the default Fabric runtime lacked the Kusto SDK. The documented Lakehouse Copy connector supports Organizational Account authentication; API creation of that exact connector is unverified. A direct-item connection with `Connection=none` and a preview shareable connection are distinct and do not establish that the required connector can be created through the API. Do not treat a draft definition as a deployed, working connection.

The [connection creation request schema](https://learn.microsoft.com/en-us/rest/api/fabric/core/connections/create-connection#createcredentialdetails) does not list an OAuth2 credentials request subtype, although the response credential-type enum lists OAuth2. The [Fabric skill connection guidance](https://github.com/microsoft/skills-for-fabric/blob/main/plugins/fabric-skills/skills/dataflows-authoring-cli/references/connection-management.md) states that OAuth2 connections cannot be created through POST. This does not imply OAuth2 is unsupported by Fabric: the Demo 3 owner reports creating a ShareableCloud/Lakehouse/OAuth2 connection through the UI, with no new grants. Its compatibility with the actual Copy pipeline remains unverified.

Preflight identified workspace creation via `POST /v1/workspaces` with `capacityId`, followed by assigned ID and region readback, and item creation with 201/202 long-running-operation handling and definition readback. Managed MLV scheduling has a public API. The Demo 1 owner reports that an explicit fixed-schema bronze definition against an empty landing folder failed with `MLV_INGEST_SCHEMA_INFERENCE_FAILED` / `UNABLE_TO_INFER_SCHEMA`. After the user authorized a separate bootstrap, a header-only CSV enabled bronze and silver creation; on-demand and five-minute scheduled lineage runs completed with zero rows and intact schemas in both. The test schedule was disabled and read back disabled. The header-only file remains; no one-row fallback or deletion/full-refresh test was needed or performed. Per-view refresh modes and measured-data behavior remain unverified. A proposed KQL queued-ingestion path pairs `ingestIfNotExists` with the corresponding `ingest-by:` extent tag and requires asynchronous verification; this is not evidence that concurrent submissions are exactly once. OneLake event property bindings require a captured runtime payload. Copy documentation describes Tables Upsert, but does not establish safe write serialization or recovery. None of these paths has been demonstrated end to end in this tenant.

## Orchestration

Requires Python 3.9 or later. From the repository root, for example:

```powershell
python scripts\deploy-demos all --dry-run --config C:\path\to\config.json
python scripts\deploy-demos demo-1,demo-3 --validate-only --config C:\path\to\config.json
python scripts\deploy-demos all --deploy --config C:\path\to\config.json
python scripts\deploy-demos all --deploy --run-data --config C:\path\to\config.json
python scripts\deploy-demos demo-1 --cleanup --yes --config C:\path\to\config.json
```

`--concurrency` overrides the configured limit (1–4); `--prefix` overrides the configured prefix. Selected tracks run independently in parallel up to that limit, and the shared producer is included in deployment and validation. Partial cleanup excludes the shared producer to avoid disrupting other demos; `all --cleanup --yes` includes it. Each track must restrict cleanup to resources it owns and require `--yes` for destructive replacement. No cleanup is automatic.

Each invocation creates a separate directory under `.deployment-state` (override with `--state-dir`) with per-track logs, result JSON and an aggregate `summary.json`. A missing entry point, invalid response, timeout, failure or blocked track makes the command fail without masking the other selected results. A timeout does not prove that work already submitted to a remote service has stopped; inspect its job state before retrying.

The sanitized [deployment inventory](scripts/deployment-inventory.json) is a point-in-time record of independently verified demo-owned resources and known shared grants, not an authoritative live registry. Refresh ownership and scope before making changes or cleaning up.

The producer is never started unless `--deploy --run-data` is explicitly supplied. This first deploys all selected destinations and the shared producer, then invokes fresh `validate-only` checks for every selected track. It starts the shared producer only if all report `pass` and `ready: true`; missing, awaiting-approval or unverified capabilities must report blocked. When Demo 2 is selected, the orchestrator then starts its independent bounded verification monitor and requires an authoritative job and heartbeat readback for the configured run and manifest before starting the producer. Monitor startup or readiness failure triggers an owned-job stop attempt; an unsuccessful stop must be investigated. Other demo selections do not start a Demo 2 monitor.

A nonempty stable `data.run_id`, bounded file count, batch size and sufficient positive maximum duration are required. The producer owns enforcing its runtime deadline, persisting progress and terminating its Fabric job; `run-data` may pass only after terminal completion and reconciliation for all selected destinations. For Demo 2, the orchestrator then waits separately for its monitor's terminal completion and per-batch and run-level verification; producer success or a running heartbeat alone is insufficient. If producer execution fails or times out, its remote outcome is uncertain; the Demo 2 monitor remains bounded rather than assuming the producer stopped. Inspect both remote jobs and their persisted outcomes. After a run, verify job/session completion and pause demo-owned schedules and rules, leaving the capacity running at its final size. The current producer remains blocked: launcher job-ID persistence, cancellation and terminal readback are not yet implemented and verified.

Local validation results coordinate checks; they are not authenticated proof or a security boundary. Immediately before a producer run, the producer must independently re-read the actual runtime identity, target IDs, access and selected-destination feature state from authoritative services, failing closed if any required check cannot be verified. Even fresh readbacks have a time-of-check/time-of-use gap. The producer owner reports that item readback returned null `defaultIdentity` for its notebook and pipeline; the earlier no-sales identity probe does not establish the identity of a future run. The current producer remains blocked and does not implement these live checks.

## Version 1 integration contract

Each track supplies `deploy.py`, invoked with `--mode`, `--config` (absolute JSON path), `--prefix`, `--state-dir` and `--result` (absolute JSON path). Modes are `dry-run`, `validate-only`, `deploy`, and `cleanup`; cleanup receives `--yes`. A user-provided `--yes` is also forwarded in other modes to authorize explicitly requested destructive replacement. The shared producer additionally supports `run-data` and receives `--selected-demos` as a comma-separated list. It must not start a producer job in any other mode. Demo 2's `start-monitor`, `monitor-status`, `wait-monitor` and `stop-monitor` modes also receive `--selected-demos`; only `start-monitor` starts its bounded verification job. `wait-monitor` must check the terminal job and notebook exit, every expected batch outcome and run-level reconciliation; missing or failed evidence must never pass. Track scripts must support safe reruns, ownership checks, bounded execution, explicit approvals and per-track manifests as specified.

Each invocation writes the requested result JSON:

```json
{"contract_version":1,"track":"demo-1","mode":"validate-only","status":"pass","ready":true,"diagnostics":[]}
```

`track` is `demo-1`, `demo-2`, `demo-3`, or `shared`; status is `pass`, `fail`, or `blocked`. Exit zero only for `pass`. Failures and blockers require nonempty sanitized diagnostics and `ready: false`. A pass for `deploy` or `validate-only` requires `ready: true`, based on actual readbacks of deployed artifacts, dimensions, configuration, identity and permissions, not just a successful API submission. Demo 2's `monitor-status` likewise requires `ready: true`, based on live job and per-instance heartbeat readbacks plus an independent storage-access check. Its `wait-monitor` also requires `ready: true`, with a `completed` sidecar and authoritative terminal reconciliation. Dry-run and cleanup need not report readiness. Never claim an unsupported automation or unapproved manual step is ready. Track logs are captured independently.

The Demo 2 monitor implementation is pending; these are its required interface and behavior, not a claim that the controller has been deployed. Monitor start must persist an immutable `demo-2-monitor-start.json`, and start and status must atomically write `demo-2-monitor.json` in the invocation state directory. Each contains `contract_version: 1`, `run_id`, `job_id`, `state`, `manifest_uri`, and timezone-aware `deadline_utc`. The start record's lifecycle state may remain `submitted` while the status sidecar transitions to `running`. Status reports `running` only after checking the live job and heartbeat for that exact run and URI. Stop must target only the job in the immutable start record and verify termination; if submission may have succeeded but no exact job ID was durably recorded, termination is unconfirmed. If the observed start record changes, the orchestrator refuses to guess which job to stop and reports termination unconfirmed. The orchestrator requires matching job/run/URI/deadline across both files, a future bounded deadline, and the producer's derived manifest URI: `https://onelake.blob.fabric.microsoft.com/<shared.workspace_id>/<shared.staging_lakehouse_id>/Files/producer/runs/<data.run_id>/manifest.json`. If supplied, `shared.run_state_location` must match that derived runs root. The maximum monitor lifetime is two track timeouts plus the producer's maximum duration and the effective Demo 2 verification timeout. The controller must record per-batch verification results separately from the producer's single-writer manifest, anchor each deadline to accepted submission, and exit on completion or deadline, including failures. It must not report propagation-latency statistics. A missing pre-start manifest is bounded waiting, not proof of access or readiness. Local evidence is a coordination aid, not authenticated proof.

The Demo 2 owner reports that generic item-job GET omits notebook exit values; the notebook-specific `jobs/execute/instances` GET with `beta=true` returns `properties.exitValue`. A completed notebook job alone does not establish that its verification passed. The owner also reports that `Skipped_IngestByTagAlreadyExists` plus matching KQL rows does not by itself prove a serialized replay; measured verification must fail closed until the prior source and serialization are established.

The CSV contract uses UTF-8 without BOM, header and comma delimiter, standard double-quote escaping, LF line endings, no null fields, ISO dates and UTC ISO timestamps ending in `Z`. Fixed header order:

```text
SalesLineID,BatchID,SaleTimestamp,CustomerID,ProductID,Date,Quantity,UnitPriceMinorUnits,SalesAmountMinorUnits
```

Minor units are integer USD cents in the current producer; do not select another currency without updating and verifying the producer contract. Each generated file has a stable run ID, batch ID, immutable filename and SHA-256 checksum over its exact staged bytes. The source manifest has top-level `contract_version: 1`, `run_id`, `config`, `destinations`, and `batches` (an object keyed by batch number as a string). The Fabric runner also persists `scheduler` lifecycle state (`running`, `completed`, or `failed`) and its terminal result and finish time. Each batch records `batch_id`, `batch_number`, `batch_class` (`measured`, `bootstrap`, or `negative-test`), `filename`, `sha256`, `row_count`, `sales_amount_minor_units`, grouped totals in `amount_by_date`, `amount_by_product_category`, and `amount_by_customer_region`, `generated_at_utc`, and destination-keyed `deliveries` containing `status` and `timestamp_utc`. Delivery records retain submission status and outcome time separately from subsequent verification. Amount totals are exact integer sums; measured totals exclude bootstrap and negative-test batches. Delivery retries use the same staged bytes and batch identity. Destination-specific validation and state remain in the corresponding track.

Demo 1's manifest validator accepts a locally staged producer manifest; this does not prove deployment or ingestion. The integrated producer includes Fabric delivery and ledger components, but its coordinated measured launcher remains blocked until its live readiness and lifecycle checks are verified.

The implementation must verify shared contract changes against all tracks before use. The specification remains the authoritative source for the data model, source manifest, isolation, verification and lifecycle requirements.
