# Chanel Fabric ingestion demonstrations

The [specification](SPECIFICATION.md) defines three isolated comparisons using the same staged CSV bytes: [file-backed materialized lake views](demo-1-materialized-lake-views/), [Eventhouse and OneLake availability](demo-2-eventhouse/), and [OneLake events with Copy](demo-3-onelake-events-copy/). The [shared producer](demo-data-generator/) runs as a bounded Fabric notebook through a wrapper pipeline in its own workspace, not as a local presentation-time process.

**Native recurring launch is not yet ready.** The current local prepared profile
is single-use and still needs a separately started monitor; it is not a reusable
presenter-facing Run button. No coordinated 10-file run has been verified.

The default one-minute source cadence is not a downstream visibility guarantee. Demo 1 uses managed MLV refresh (document the actual supported interval); Demo 2's five-minute OneLake target is not an SLA and its propagation latency is not reported; Demo 3 requires a real event and Copy run. See the specification for acceptance criteria and feature-specific blockers.

The user has approved access and other changes needed for live testing; determine and record the least-privilege scope before making changes. ## Orchestration

Requires Python 3.9 or later. From the repository root, for example:

```powershell
python scripts\deploy-demos all --dry-run --config C:\path\to\config.json
python scripts\deploy-demos demo-1,demo-3 --validate-only --config C:\path\to\config.json
python scripts\deploy-demos all --deploy --config C:\path\to\config.json
python scripts\deploy-demos all --deploy --run-data --config C:\path\to\config.json
python scripts\deploy-demos demo-1 --cleanup --yes --config C:\path\to\config.json
```

The user clarified that parallelization means working on the three largely independent demo implementations in parallel. Serial deployment is acceptable; concurrent deployment is not a readiness gate. Existing safe orchestration is retained while work focuses on the shortest route to runnable demos.

`--concurrency` overrides the configured limit (1–4); `--prefix` overrides the configured prefix. Selected tracks run independently in parallel up to that limit, and the shared producer is included in deployment and validation. Partial cleanup excludes the shared producer to avoid disrupting other demos; `all --cleanup --yes` includes it. Each track must restrict cleanup to resources it owns and require `--yes` for destructive replacement. No cleanup is automatic.

The configured `tenant_id` must be a UUID. Deployment ownership and recovery state persist in `.deployment-state/<prefix>-<tenant-id>` (override the root with `--state-dir`); each invocation keeps separate logs, result JSON and `summary.json` in its `runs` subdirectory. An exclusive `.orchestrator-v1.lock` prevents overlapping operations on the same state. A crash can leave that lock behind: reconcile remote jobs and owned state before manual recovery, and never automatically remove it. Prior versions stored track state inside individual root-level `run-*` directories; recognized legacy state blocks non-dry-run operations until its ownership and pending work are reviewed and it is safely migrated or a separate state root is chosen. A missing entry point, invalid response, timeout, failure or blocked track makes the command fail without masking the other selected results. A timeout does not prove that work already submitted to a remote service has stopped; inspect its job state before retrying.

The sanitized [deployment inventory](scripts/deployment-inventory.json) is a point-in-time record of independently verified demo-owned resources and known shared grants, not an authoritative live registry. Refresh ownership and scope before making changes or cleaning up.

The orchestrator never starts the measured producer unless `--deploy --run-data` is explicitly supplied. This first deploys all selected destinations and the shared producer, then invokes fresh `validate-only` checks for every selected track. Standalone `--validate-only` uses the same resolution before checking. If the producer workspace or staging Lakehouse ID is absent, the producer's journal is used to resolve candidate IDs into a per-invocation effective configuration; candidate resolution requires tenant, capacity, producer identity ID and workspace name, and explicit conflicting IDs block. Each selected track also resolves its own target candidate from its ownership journal. The effective `shared.target_bindings` contains exactly the selected targets; supplied bindings and per-track IDs/names must match their candidates, and producer and demo workspaces must be distinct. Unselected bindings remain unchanged in the original config. Standalone validation still reports independent track results when resolution fails, but the overall command fails. The original config is never modified. Journals and local sidecars are provisional, not proof of ownership or live readiness. The same effective configuration is supplied to all fresh validations and subsequent monitor and producer operations. It starts the shared producer only if all report `pass` and `ready: true`; missing, awaiting-approval or unverified capabilities must report blocked. When Demo 2 is selected, the orchestrator then starts its independent bounded verification monitor and requires an authoritative job and heartbeat readback for the configured run and manifest before starting the producer. Monitor startup or readiness failure triggers an owned-job stop attempt; an unsuccessful stop must be investigated. Other demo selections do not start a Demo 2 monitor.

The orchestrator compares configuration snapshots with the in-memory invocation configuration at phase boundaries, including after validation and monitor startup. An observed change blocks producer dispatch; if a monitor was submitted, it attempts to stop only its exact recorded job using the original configuration, with a fresh recovery snapshot if necessary. A change during producer execution makes its outcome unconfirmed. These checks do not authenticate the file or prevent a concurrent writer from changing it between checks; protect the deployment state directory from other writers.

A nonempty stable `data.run_id`, bounded file count, batch size and sufficient positive maximum duration are required. The producer owns enforcing its runtime deadline, persisting progress and terminating its Fabric job; `run-data` may pass only after terminal completion and reconciliation for all selected destinations. For Demo 2, the orchestrator then waits separately for its monitor's terminal completion and per-batch and run-level verification; producer success or a running heartbeat alone is insufficient. If producer execution fails or times out, its remote outcome is uncertain; the Demo 2 monitor remains bounded rather than assuming the producer stopped. Inspect both remote jobs and their persisted outcomes. After a run, verify job/session completion and pause demo-owned schedules and rules, leaving the capacity running at its final size. The bounded one-file customer run has not yet been completed; it does not replace ten-file acceptance.

The producer entry point also offers direct `producer-status` and `stop-producer` modes for a bound **no-sales preflight** parent-job journal, using the original effective configuration and `--selected-demos`. If the parent is terminal but its exact linked notebook child is still active, `stop-producer` checks the same job chain for up to 120 seconds without requesting cancellation. The producer owner observed that the child can still be running after the parent completes. Both modes report termination unconfirmed because delivery reconciliation remains unproven; neither is grounds to stop the monitor. These inspection modes are not exposed as top-level orchestrator recovery commands.

Local validation results coordinate checks; they are not authenticated proof or a security boundary. Before staging, the producer notebook checks its actual runtime identity, selected target metadata and direct workspace write roles. Even fresh readbacks have a time-of-check/time-of-use gap. Item readback did not expose `defaultIdentity` for the notebook and pipeline; the earlier no-sales identity probe does not establish the identity of a future run.

### Spark high-concurrency sessions

Spark notebooks in the shared producer, Demo 2 verifier/monitor, and Demo 3 setup enable Fabric's high-concurrency setting. This is not runtime proof: session reuse requires compatible runs within Fabric's supported boundaries, and pipeline-triggered notebooks may need the workspace pipeline setting and matching session tags. Demo 1's owner reports an isolated Livy probe where two high-concurrency IDs with the same tag shared one Livy session ID with distinct REPL IDs; this verifies interactive Spark verification, not scheduled MLV refresh. Demo 2's two concurrent verifier jobs reported `isHighConcurrency:false` despite the notebook property; its owner-created workspace still has pipeline high concurrency disabled, and the monitor uses on-demand notebook jobs rather than pipeline activities. Read-only reconciliation confirmed two distinct settings changes: `chanel-demo-data-generator` (workspace `48593f2f-d3ac-474b-ba96-08282d6f69df`) has pipeline high concurrency enabled after a one-property change with a full before/after snapshot; `chanel-demo3-copy-events` (workspace `744223de-ceab-4c4f-82ba-f811bcb5c7d7`) also has it enabled after a separate one-property change, but its full before snapshot and comprehensive usage inventory were not retained. No further setting changes were made. Neither workspace setting proves Spark ran in a shared high-concurrency session; Demo 3 runtime evidence is pending. Capture actual session type and IDs for each supported path, and claim reuse only when compatible activities share a session ID. If an activity cannot use the supported high-concurrency path, document its actual mode and the limitation. See the [high-concurrency course correction and safeguards](SPECIFICATION.md#13-user-decisions-and-course-corrections).

High concurrency is only a possible Spark startup optimization. It does not fix or prove Demo 3 event delivery, Activator execution, Copy completion, missed-event recovery, or SQL freshness; treat any Demo 3 improvement as a hypothesis until measured independently.

## Version 1 integration contract

Each track supplies `deploy.py`, invoked with `--mode`, `--config` (absolute JSON path), `--prefix`, stable `--state-dir` and per-invocation `--result` (absolute JSON paths). Modes are `dry-run`, `validate-only`, `deploy`, and `cleanup`; cleanup receives `--yes`. A user-provided `--yes` is also forwarded in other modes to authorize explicitly requested destructive replacement. The shared producer additionally supports `run-data` and the read-only recovery inspections; these and its `validate-only` receive `--selected-demos` as a comma-separated list. If candidate resolution fails, independent validation still receives the selection and original config snapshot but must block on missing bindings. Its local-only `resolve-candidate-ids` mode writes `shared-producer-candidate-ids.json` alongside the requested result, with exactly `version`, `workspace_id` and `staging_lakehouse_id`; a successful result is not readiness. Each selected destination must also implement the local-only `resolve-target-candidate` mode: after checking its own stable, non-pending ownership journal, it exclusively creates `<track>-target-candidate.json` alongside the requested result with exactly `contract_version`, `track`, `tenant_id`, `prefix` and `target`. The target contains exactly `workspace_id`, `item_id` and `fact`; UUIDs are canonical, lowercase and nonzero. A successful candidate result is `pass`, `ready: false`; it makes no cloud changes and is not ownership or readiness proof. Missing or ambiguous journals must block rather than adopting existing resources by name. The producer must not start a job in any other mode. Demo 2's `start-monitor`, `monitor-status`, `wait-monitor` and `stop-monitor` modes also receive `--selected-demos`; only `start-monitor` starts its bounded verification job. `wait-monitor` must check the terminal job and notebook exit, every expected batch outcome and run-level reconciliation; missing or failed evidence must never pass. Track scripts must support safe reruns, ownership checks, bounded execution, explicit approvals and per-track manifests as specified.

The target candidates are expectations only. `fact` identifies the actual destination, including case where the service is case-sensitive; an explicitly configured target must match it exactly. The v1 candidate does not include or authenticate the owning journal's identity or marker; a prefix-shaped live marker or an additional local field cannot establish ownership. The producer implements selected workspace/item and adapter metadata readbacks and a case-sensitive Demo 3 Delta table listing check with the CLI principal. Direct read-only calls to the selected-target helper matched the observed workspace/item and configured adapter identities for all three demos in MCAP using provisional candidates, including Demo 3's `dbo.factsales` physical path. These checks alone cannot establish landing-to-fact linkage, ownership or measured-runtime access. Before writes, use existing trusted deployment records, fresh target readbacks and actual runtime access checks; a candidate sidecar or stored `ready` flag is not sufficient. A new cross-track provenance framework is not required when existing checks suffice. Global retained-key census and cross-destination writer fencing are not required solely to preserve run-global `SalesLineID` uniqueness. Destination-specific write serialization, idempotent `(BatchID, SalesLineID)` replay, ownership, permissions, and lifecycle/safe-stop checks remain required. Normal-run integration and readiness checks are incomplete, so measured execution remains blocked.

To reuse a Demo 2 deployment created under a different owner scope, set both `demo-2.deployment_prefix` and `demo-2.deployment_state_dir` to its original prefix and existing absolute state directory. Direct producer `run-data` also accepts these paired fields for Demo 1 and Demo 3, routing their admission checks to the original journals; the top-level orchestrator currently routes only Demo 2. Original journals and monitor records must stay intact. These settings route checks; they do not prove readiness or authorize a run.

For a fresh Demo 1 synthetic target, the [separate opt-in provisioner](demo-1-materialized-lake-views/README.md) relies on an operator-protected local deployment journal: record a unique marked creation intent before each POST, retain the actual accepted response or operation evidence and resulting IDs, and independently read back the exact resources, parent, tenant, capacity and markers. [Workspace creation](https://learn.microsoft.com/en-us/rest/api/fabric/core/workspaces/create-workspace) returns 201; [Lakehouse creation](https://learn.microsoft.com/en-us/rest/api/fabric/lakehouse/items/create-lakehouse) can return 201 or 202 with an operation ID. An uncertain create must not be retried or resolved by adopting a same-name resource. On 2026-11-24, one isolated MCAP Workspace and schema-enabled Lakehouse were created with 201 receipts and independently read back. The Demo 1 owner reports that native Bronze and replay-aware Silver MLVs were then created and refreshed: a batch, its renamed identical replay and a second batch reusing an ID produced three Bronze rows and two correctly keyed Silver rows totaling 3,000 minor units. This is a local-state trust model, not Fabric creator attestation: a writable journal or mutable description can be forged, and an exclusive state lock is not access control. The synthetic result does not establish runtime access for the shared producer or measured readiness.

Each invocation writes the requested result JSON:

```json
{"contract_version":1,"track":"demo-1","mode":"validate-only","status":"pass","ready":true,"diagnostics":[]}
```

`track` is `demo-1`, `demo-2`, `demo-3`, or `shared`; status is `pass`, `fail`, or `blocked`. Exit zero only for `pass`. Failures and blockers require nonempty sanitized diagnostics and `ready: false`. A pass for `deploy` or `validate-only` requires `ready: true`, based on actual readbacks of deployed artifacts, dimensions, configuration, identity and permissions, not just a successful API submission. Demo 2's `monitor-status` likewise requires `ready: true`, based on live job and per-instance heartbeat readbacks plus an independent storage-access check. Its `wait-monitor` also requires `ready: true`, with a `completed` sidecar and authoritative terminal reconciliation. Dry-run and cleanup need not report readiness. Never claim an unsupported automation or unapproved manual step is ready. Track logs are captured independently.

The Demo 2 monitor lifecycle CLI is implemented locally, but its live producer/destination readiness gates remain blocked; a global sales-line reservation is not required by the revised contract, and this is not a claim that the controller has been deployed. Each contains `contract_version: 1`, `run_id`, `job_id`, `state`, `manifest_uri`, timezone-aware `deadline_utc`, the selected `target_bindings`, `generator_sha256`, `producer_config`, and `monitor_binding_sha256`. The binding hashes canonical sorted compact UTF-8 JSON of the targets, normalized generator SHA-256, and producer config. The start record's lifecycle state may remain `submitted` while the status sidecar transitions to `running`. The CSV contract uses UTF-8 without BOM, header and comma delimiter, standard double-quote escaping, LF line endings, no null fields, ISO dates and UTC ISO timestamps ending in `Z`. Fixed header order:

```text
SalesLineID,BatchID,SaleTimestamp,CustomerID,ProductID,Date,Quantity,UnitPriceMinorUnits,SalesAmountMinorUnits
```

Minor units are integer USD cents in the current producer; do not select another currency without updating and verifying the producer contract. Each generated file has a stable run ID, batch ID, immutable filename and SHA-256 checksum over its exact staged bytes. `SalesLineID` is `1..row_count` within each batch and stable on replay; the fact/replay key is `(BatchID, SalesLineID)`, so line IDs may repeat across different batches and runs. The source manifest has top-level `contract_version: 1`, `run_id`, `config`, `destinations`, and `batches` (an object keyed by batch number as a string); it has no global sales-line reservation fields. The Fabric runner also persists `scheduler` lifecycle state (`running`, `completed`, or `failed`) and its terminal result and finish time. Each batch records `batch_id`, `batch_number`, `batch_class` (`measured`, `bootstrap`, or `negative-test`), `filename`, `sha256`, `row_count`, `sales_amount_minor_units`, grouped totals in `amount_by_date`, `amount_by_product_category`, and `amount_by_customer_region`, `generated_at_utc`, and destination-keyed `deliveries` containing `status` and `timestamp_utc`. Delivery records retain submission status and outcome time separately from subsequent verification. Amount totals are exact integer sums; measured totals exclude bootstrap and negative-test batches. Delivery retries use the same staged bytes and batch identity. Destination-specific validation and state remain in the corresponding track.
