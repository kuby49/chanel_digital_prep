Ingest in Kusto. Read in OneLake.

The shared producer emits immutable sales CSV batches. This path writes to Eventhouse first, then exposes the KQL data in a format that Lakehouse engines can read.

Closest Databricks patternAuto Loader into a Unity Catalog Delta table, read by downstream SQL or Spark. Similar destination for file ingestion, but no KQL store or KQL-to-OneLake mirroring step.

02 / 06 · Demo 2 · Technical detail

Ingestion and mirroring have separate clocks.

Use KQL to check committed batches first. Verify the Lakehouse shortcut separately; a successful KQL read does not prove Delta visibility.

Write and verify in KQL

  • The presenter path uses inline Kusto ingestion for small demo batches. This is not a production recommendation; use supported queued ingestion for sustained loads. The repository includes a queued CSV adapter with explicit header and schema mapping.
  • Reconcile per-batch row counts, distinct (BatchID, SalesLineID) keys and exact integer minor-unit totals. Check replay rather than assuming exactly-once ingestion.

Enable and verify OneLake

  • Enable OneLake availability on the KQL database separately; verify the table policy. Reset does not automatically re-enable a manually disabled database toggle.
  • The configured five-minute mirroring target is not an SLA. The read-only Delta output follows database retention, is not the original CSV and needs no extra Lakehouse Copy activity.
Databricks: direct Delta writeAuto Loader tracks file discovery with a checkpoint and writes to Delta; downstream engines read that table. There is no separate Eventhouse mirroring policy, KQL surface or OneLake toggle to match.

Refresh the lineage, not every file.

Fabric Materialized Lake Views read the landing folder directly and materialize both bronze and silver. No Copy activity or ingestion notebook sits in the data path.

Closest Databricks patternA Lakeflow Spark Declarative Pipelines streaming table for bronze, then a materialized view for silver. Comparable layering, not the same file-backed MLV primitive.

04 / 06 · Demo 1 · Technical detail

Refresh order matters more than arrival order.

The producer lands files every minute in the bounded demo. The five-minute Fabric-managed schedule refreshes bronze before silver; it need not run for every arrival.

File contract and lineage

  • USING OneLake_Files uses explicit CSV schema and parsing. Keep source identity and separate the bootstrap from measured sales.
  • Read actual refresh mode and timing in history. APPEND_ONLY describes the configured bronze file refresh mode; it is not evidence that a specific bronze or silver refresh executed incrementally.

Validate the silver result

  • Reconcile bronze rows, recorded rejections and silver facts. Casting or failed dimension joins must not silently lose valid sales.
  • Check grouped totals, unique (BatchID, SalesLineID) keys and expected row counts after another refresh. That check does not establish deduplication for the same rows copied under a new filename.
Databricks: streaming table plus materialized viewUse Auto Loader (for example, STREAM read_files) for incremental file discovery into bronze. Define silver as a materialized query with joins. Databricks can use incremental or full refresh depending on the query and compute; inspect its own refresh evidence.

05 / 06 · Demo 3 · Data flow

Trigger Copy for the file that arrived.

The file-created notification carries identity, not sales rows. Activator starts a Data Factory pipeline; Copy reads the specific CSV identified by the event.

Closest Databricks patternA Lakeflow Jobs file-arrival trigger starts a job that uses checkpointed Auto Loader to process newly discovered files. A job run may cover multiple files; it is not an exact-file event binding.

06 / 06 · Demo 3 · Technical detail

Append needs a replay guard.

Separate event delivery, file readiness, Copy completion and target visibility. A delivered event is not evidence that the rows were written.

Bind one event to one file

  • Pass the subject and event ID to the pipeline. Check readiness and resolve the exact filename; Copy maps the CSV columns into the typed Delta target.
  • Verify the target batch with row counts, unique (BatchID, SalesLineID) keys and exact totals. Correlate the event, path, batch and pipeline run in the audit.

Do not blindly retry

  • Current Copy behavior is append, not upsert. Serialize writes and reconcile destination state before replaying an uncertain append; a write may succeed before the audit does.
  • The demo assumes notifications are not missed. That assumption is not proof of delivery or exactly-once processing. Verify duplicate/retry outcomes in the destination.
Databricks: arrival-triggered job plus checkpointA file-arrival trigger watches a location. Auto Loader with AvailableNow can process all pending files in a job run. Preserve its checkpoint; separately handle business-key duplicates. Neither replaces Fabric's per-event subject binding or guarded Copy.
